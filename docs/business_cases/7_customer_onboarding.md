# Accelerate customer onboarding and upgrades

For SAP partners, winning a new customer often triggers weeks of technical
reconstruction: identify the current solution baseline, collect transports,
resolve prerequisites, adapt package names, and repeat setup activities.

TRM turns the approved solution baseline into installable packages.

## Onboard from a known release

Instead of building a transport bundle for each new project, the partner selects
the package versions that represent the customer's contracted solution. TRM can
install their compatible dependencies, check SAP prerequisites, map the package
hierarchy to the customer's naming conventions, and execute declared setup
activities.

This creates a more consistent starting point across projects. Consultants can
focus on customer-specific configuration and extensions instead of reconstructing
the shared product foundation.

## Make upgrades a product process

The same approach applies after go-live. A defect correction or feature is
published as a new semantic version. Each customer can adopt it according to an
agreed maintenance window, while the partner preserves a clear relationship
between customer state and product release.

For complex solutions, components can be versioned independently. Customers only
upgrade the modules they use, subject to declared compatibility constraints.

## Benefits for both parties

The partner gains lower onboarding effort, repeatable delivery, and a clearer
support baseline. The customer gains visibility into what is being installed,
retains approval control, and can promote the generated transport through its
normal landscape.

Neither party has to rely on a consultant remembering which historical transport
belonged to which customer release.

## A stronger handover

A package name, version, manifest, and repeatable installation workflow make the
technical handover match the commercial promise: the customer receives a defined
software release, not merely a collection of changes.
